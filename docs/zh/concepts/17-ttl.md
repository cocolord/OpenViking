# TTL 分阶段交付

第一阶段只交付 TTL 所需的内部严格删除能力。TTL 配置、到期判断、读取过滤、扫描器、失败登记和重试调度在后续阶段接入。

## 内部删除契约

TTL 以内部 ROOT 上下文调用 `VikingFS.rm(uri, recursive=True, ctx=ctx, strict=True)`，其他角色不得使用严格模式。HTTP、MCP、SDK 和 CLI 不暴露 `strict` 参数；普通删除保持原行为。

严格删除复用现有权限检查和路径锁，依次执行：

1. 按当前账号和完整 URI 范围删除向量，包括文件已不存在的孤儿向量。目录范围覆盖自身及后代，不包含相似前缀的兄弟目录。
2. 用相同范围确认向量计数为零。未配置向量后端、删除失败、计数失败或仍有残留均返回失败，保留文件。
3. 删除文件或目录，再绕过元数据缓存确认目标已不存在，并再次确认向量无残留。只接受有类型依据的文件不存在错误；网络错误中的“not found”不能代表删除完成。

后端限流、故障和超时保留原异常及错误码；确认发现残留时抛出 `StorageException(action="confirm_delete", retryable=True)`。调用方收到异常就不能登记为删除完成。`estimated_deleted_count` 仍是估计值，不能作为成功依据。

重复调用同一 URI 可以继续删除，即使文件已不存在。系统 ROOT 清理直接按 URI 范围删除向量，无需为收集向量 URI 遍历文件树。

## 后续 TTL 接入

后续调度层持久化账号、URI 和失败原因，负责有界退避重试及长期失败降频。严格删除内部不自动重试，也不新增任务或失败存储。即使最后的确认请求失败时数据实际已经删除，本次仍报告失败，可按原 URI 重试。

本阶段确认本次存储操作的完成情况。TTL 接入时仍须协调过期复核、异步写入和同 URI 重建，避免旧任务写回或误删新对象；上线本阶段不表示 TTL 已启用，也不证明云端计费已停止。
