# Compile 多模态素材读取

## 已确认的需求

PR #6719 的讨论确认：Compile 应复用 `openviking_multi_read` 的读取能力，使用图片里的信息；`read_raw` 保持原始文本读取职责。图片二进制不能作为文本行证据，拒绝图片只是原 PR 的临时保护。

以下是为实现该需求整理的技术方案，具体实现选择不代表讨论参与者已逐项确认。

## 读取与证据

- 从 `VikingMultiReadTool` 抽出共用的结构化批量读取方法，普通工具调用与 Compile 都使用它。Compile 使用任务原有的鉴权 client，不另建账号或连接。
- 文本素材读取原文，保持现有切分、行号、字符范围和哈希。普通聊天工具的可见文本行为保持不变。
- PNG、JPEG、GIF、WebP 使用现有下载、格式识别和大小检查，生成原生 `image_url`。Compile 为图片登记原 URI、图片字节哈希和媒体类型，不生成虚假的文字行号。其他图片格式明确报不支持。
- 图片在任务私有源证据中保存一次；模型请求把图片作为原生媒体部分传递，JSON 只包含来源描述。直接生成、Map、Reduce、证据重读和 agent 子任务使用同一表示。
- 图片引用使用已有的 source ID；图片不接受文本行范围。来源覆盖、缓存和恢复继续绑定原始图片哈希。
- 音视频复用普通读取工具已有的文字概览，并明确标记为派生语义内容；没有概览时返回明确错误，不读取二进制文本。

## 边界与代价

场景是包含文字和图片的资料目录，图片总数没有已知上界，因此按现有读取并发、每次最多 4 张图片及累计媒体字节预算分批。单张或一次模型请求超限应返回明确诊断，不静默丢图。多图素材超出直接生成预算时交由现有分阶段流程处理。

不新增独立的图片摘要模型调用，也不新增依赖或对外接口。直接传图会增加任务源证据存储、请求体、视觉 token 和后续核对时重复传图的成本；以已有摘要替代原图更省，但会损失图片独有细节，因此本次图片路径选择原图。暂不宣称成本数值或吞吐提升，均未实测。

沿用当前 provider 对原生工具媒体的能力边界（包含主备配置），不扩大适配器支持范围。不支持时明确报错；图片导入时可被视觉模型理解，不等于 Agent 工具结果可以传图。

## 验证

验证文本原文不变、图片字节不进入文本切分、原图以媒体部分进入模型、图片来源与哈希保留、直接与分阶段读取一致、按需重读可返回图片，以及格式/容量/provider 限制明确报错。使用文字里没有、仅图片里有的 `RETRY LIMIT: 7` 合成素材覆盖输入到产物的引用链路。模拟 provider 的链路测试与真实视觉模型的效果验收分别报告。
